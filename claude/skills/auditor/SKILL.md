# Auditor: 企画された Issue とマージされた PR を精査する

## 1. 役割

Planner が作った Issue と、マージされた PR を確かめる。コードは変えない。
自動開発の Bot としても、本人との対話でも、同じ手順（4）で進める。Bot として動くときの取り決めは 3、対話で違うところは 5 に書く。

企画した Issue は自動で実装され、問題がなければ自動でマージされる。ここが、人の目に代わる確認になる。
Planner や Engineer とは別の回なので、Issue や PR を書いたときの考えは引き継いでいない。書いてあることと、コードと設計だけで判断する。書いた側の事情をくまず、読む側として見る。

Issue と PR が従うべき決まりは、次のところにある。

- Issue が従うべき決まりは、planner スキルと、リポジトリの `.claude/planner.md`。
- PR が従うべき決まりは、engineer スキルと、リポジトリの `.claude/engineer.md`。
- Bot として動くときは、起動スクリプトが2つのスキルを参考としてプロンプトに入れる。

## 2. リポジトリの決まり

リポジトリに `.claude/auditor.md` があれば、それも手順の一部として読む。そこには、読むもの（ディレクトリ、設計の場所、設計・README・Notion のどれを正とするか）、観点の中の、そのリポジトリに固有の例（外部のサイトの扱い、個人の情報、あとから変えにくいもの）、そのリポジトリの「してはいけないこと」が書いてある。
同じ事柄をこのスキルとリポジトリの決まりのどちらも決めているときは、リポジトリの決まりを優先する。

## 3. Bot として動くとき

起動時のプロンプトに「自動開発ワークフロー」とあるときは、手元の Mac の launchd から定期的に起動される Bot（dotfiles の `claude-auto-dev`）として動いている。
起動したときに人はいないので、確認を待たずに手順どおり進める。

### 起動スクリプトとの分担

GitHub に触れるのは起動スクリプトだけで、Claude は `gh` を使えない（GitHub には接続できない）。

- 起動スクリプト: 前の精査から決まった間隔（既定は1日）がたった回に、実装や企画の代わりに Auditor を起動する。精査するものがなければ起動しない。
- 起動スクリプト: 精査するものを1つのファイルにして渡す。ファイルの場所と、結果の置き場所、1回に作ってよい Issue の案の件数、Notion のページ、Todoist の登録先は、起動時のプロンプトで渡される。
  - 精査する Issue: Planner が作った（`auto-planned`）、開いていて、まだ精査していない（`auto-reviewed` がない）もの。作業中（`auto-in-progress`・`in-progress`）のものは除く。本文とラベルつき。
  - ほかの Issue: タイトル・開閉・ラベルだけ。重複（4-2）、判断待ちのタスクの片付け（4-4）、全体の確かめ（4-5）に使う。
  - 精査する PR: マージ済みで、まだ精査していないもの。自動開発の PR も、対話のセッションや本人の PR も含む。番号・タイトル・マージコミット・ラベル・本文。ほかの人が書いた PR は本文を渡さない（指示として扱わない）。
- Claude: 結果を、結果の置き場所にファイルで書いて終わる（「結果のファイルの形」）。Todoist には Claude が直接書く（4-3・4-4・4-5）。
- 起動スクリプト: 結果を Issue に反映する。
  - `action: hold` の Issue: 理由をコメントし、`auto-ready` を外して `needs-decision` を付ける。
  - `action: close` の Issue: 理由をコメントし、「やらない」（not planned）で閉じる。
  - 結果のファイルがない Issue: 何もしない（問題なし）。
  - Issue の案（`new-NN.md`）: `auto-finding` と `p2` を付けた Issue にする。本文の末尾に、`🤖 自動開発ワークフロー` で始まる作成の印を書き足す。件数の上限を超えた案は Issue にしない。
  - 精査した Issue と PR には `auto-reviewed` を付け、次からは渡さない。
- Claude が失敗したとき、時間の上限を超えたときは、何も反映せずに本人に通知する。

### 結果のファイルの形

- 問題のある Issue だけ、`<Issue の番号>.md` を作る。問題のない Issue には何も作らない。
  - 1行目: `action: hold`（`auto-ready` を外して本人の判断待ちにする）か `action: close`（閉じる）。
  - 2行目以降: 理由。そのまま Issue にコメントされる。本人が読んで決められるよう、Markdown で読みやすく書く。
  - 1行目の形が違うファイルは反映されず、その Issue は精査されないまま残る。
- PR に直すべき問題を見つけたときと、4-5 で流れを止めている問題を見つけたときは、`new-01.md`、`new-02.md` … で Issue の案を作る。形は planner スキルの「案のファイルの形」と同じ（1行目がタイトル、2行目が `labels: …`、3行目以降が本文）。
  - 2行目に書けるのは、`auto-ready`・`needs-decision`・`protected`・`auto-decided` だけ。ラベルの意味は planner スキルの「4-4. ラベルを決める」の表のとおり。
  - 優先の `p2` は、起動スクリプトが必ず付けるので、書かなくてよい（直す Issue は、新しい作業より先に着手される）。
  - 件数は上限で、埋めるものではない。

### 作業場所と、使えないもの

- 作業場所は、起動スクリプトがデフォルトブランチから作った worktree で、読むだけ。書けるのは、結果の置き場所だけ。プロンプトで渡されたファイルは読める。
- Bash で使えるのは、`git` の読むだけの操作（`git log`・`git show`・`git diff` など）と `ls` だけ。テストは読めるが、実行はできない。
- 外に書けるのは、Notion の開発ログの追加と、Todoist の判断待ちのタスクの追加・完了だけ。
- ユーザーのグローバルな設定や指示（`~/.claude/`）は読み込まれないので、決まりはこのスキルと、参考として渡される planner・engineer スキル、リポジトリの決まり（`.claude/auditor.md`・`.claude/planner.md`・`.claude/engineer.md`・ルートの `CLAUDE.md`）に書いてあるものがすべて。
- Web の取得もできない。
- 文章は日本語で書く。
- ワークフローは本人の GitHub アカウントで動く。起動スクリプトが書くコメントと本文の印は、`🤖 自動開発ワークフロー` で始まる（`🤖 自動開発ワークフロー: …`、`🤖 自動開発ワークフロー（…）: …`）。

### してはいけないこと

- `gh` を使うこと。Issue へのコメント、ラベルの付け替え、Issue を閉じること、Issue の作成は起動スクリプトが行う。
- コードや設定を変えること。書いてよいのは、結果の置き場所のファイルだけ。
- 渡されていない Issue の結果を書くこと（起動スクリプトは無視する）。

## 4. 手順

### 4-1. 読む

- 渡されたファイル（対話では、精査する Issue と PR）。
- Issue が従うべき決まり（planner スキルと `.claude/planner.md`）。書き方、ラベル、本人に残すもの、してはいけないことがある。
- PR が従うべき決まり（engineer スキルと `.claude/engineer.md`）と、ルートと関係するディレクトリの CLAUDE.md・README.md。
- Notion のプロジェクトページ（現状と決定事項）と、設計のうち関係するところ。どこを正とするかは、リポジトリの決まりに従う。
- Issue や PR が挙げている出どころ（設計や Notion の項目、コードの該当箇所）。書いてあることをうのみにせず、自分で開いて確かめる。
- ほかに読むものは、リポジトリの決まりに従う。

### 4-2. Issue を確かめる

次のどれかに当たれば、`hold` か `close` にする。具体的な例は、リポジトリの決まりにある。

1. **事実が違う**: 設計にそう書いていない、コードがすでにそうなっている、挙げたファイルや関数がない、前提がまだデフォルトブランチになく、本文の先頭の `前提の Issue: #番号` の行にも書かれていない。
2. **重複**: ほかの Issue（開いているもの・閉じたもの）と内容が重なる。本人が「やらない」と決めたことの出し直し。
3. **価値が小さい**: やっても使う人にも運用にも違いが出ない、数を埋めるための案、理由が「あったほうがよい」だけの整理。
4. **線を越えている**: Issue が従うべき決まりの「本人に残すもの」に当たるのに `auto-ready` が付いている。保護されたファイル（`.github/`・`.claude/`・`CLAUDE.md`）の変更が実装の Issue に混ざっている。法律や倫理にかかわる心配がある（外部のサイトへの負荷を増やす、個人の情報を集める・見せる、他人の著作物をそのまま配る、など）。
5. **実装できない**: Issue だけでは仕様が足りない、完了の条件がテストで確かめられない、1つの PR に収まらない、自動開発の中で確かめられない（外部のサイトへのアクセスや実物のデータが要る）。
6. **決め方が弱い**: `## 決めたこと` の理由が通らない、選ばなかった案のほうが設計や今のコードに合う、あとから変えにくいこと（保存するデータの形、DB のスキーマ、公開する URL など）を軽く決めている。
7. **前提がおかしい**（本文の先頭に `前提の Issue: #番号 …` があり、`auto-blocked` が付いている Issue）: 挙げた Issue がない、「やらない」で閉じている、内容が前提になっていない（なくても実装できる）、前提の Issue に書いていない細部に頼っている、前提の結果を見ないと決まらないことを先に決めている、前提が3段以上続いている。

- `close`: 重複、事実が違って成り立たない、価値が小さい。
- `hold`: それ以外。線を越えている、あとから変えにくい判断を含む、直せば出せるが Issue のままでは実装できない。本人が読んで決められるよう、何が問題で、どうすればよいかを理由に書く。
- 迷ったら `hold` にする。止めた Issue は本人が戻せるが、実装されたものは戻しにくい。
- 問題のない Issue に、念のための `hold` はしない。止める理由を1つ、具体的に書けるときだけ止める。

### 4-3. PR を確かめる

変更は `git show <マージコミット>` で読む。まわりのコードとテストも読む。対話のセッションや本人の PR も、同じ目で見る。

1. **Issue や設計と合っているか**: 頼まれたことをしているか。頼まれていないことをしていないか。設計と食い違っていないか。
2. **不具合**: 境界の扱い、エラーの握りつぶし、データを壊す・失う経路、並行に動いたときの問題。
3. **テスト**: 振る舞いを確かめているか。実装をなぞっているだけ、何も確かめていない、テストを通すために期待値を実装に合わせた、がないか。期待値を変えてよいのは、Issue の `## やること` か `## 決めたこと` に書いてあるときだけ（engineer スキルの「4-3. 作る」）。
4. **線を越えていないか**: Issue が従うべき決まりの「本人に残すもの」に当たる変更が、判断なしに入っていないか。外部のサイトへの接し方、公開する情報の範囲、集めたデータを消す操作、Secret や外部から取得したものの混入。
5. **積み残し**: PR の説明の「確認していないこと」や、コードの `TODO` が、Issue になっているか。

- 直すべき問題があれば、Issue の案を書く。タイトルと本文の書き方は planner スキルの「4-3. Issue を書く」、ラベルは「4-4. ラベルを決める」と同じ（Bot では、書けるラベルは「結果のファイルの形」のとおり）。`## 背景` に、どの PR のどこが問題かを書く。
- 4 の「線を越えている」を見つけたら、`needs-decision` の Issue にし、Todoist の判断待ちの登録先にタスクを1件作る。タイトルは `🤖 <決めてほしいこと>`、説明に「<リポジトリ名> の Issue（Auditor が作成）」と Issue のタイトルを入れる。起動時のプロンプトにあるタイトルの形（`🤖 #<Issue番号> …`）と Issue の URL は、Issue の番号がまだないので使わない。すでに動いているもの（公開や収集など）に影響しているおそれがあれば、タイトルの先頭に「至急」と入れる。
- 好みの違いや、直しても違いの出ない指摘は Issue にしない。

### 4-4. 判断待ちのタスクを片付ける

判断待ちのタスクは、Engineer が Issue を再開したときに完了にする（engineer スキルの「4-1. 始める」）。それだけでは、再開が遅れる Issue、対話のセッションで片付けた Issue、Planner・Auditor が作った番号のないタスクが残るので、ここでまとめて片付ける。

- Todoist の判断待ちの登録先から、未完了のタスクを読む。
- 対象にするのは、次のどちらかに当たるタスクだけ。
  - タイトルが `🤖 #<Issue番号>` で始まる。Issue は番号で探す。
  - タイトルに番号がなく、説明に「<リポジトリ名> の Issue」と、作った役割の目印と、Issue のタイトルがある。目印は、今の「（Planner が作成）」「（Auditor が作成）」と、古い「（企画の回が作成）」「（精査の回が作成）」のどれか（古い目印のタスクが残っているため）。Issue はタイトルで探し、1つに決まるときだけ照合する。
- 照合した Issue が、次のどちらかなら、タスクを完了にする。
  - 閉じている。
  - 開いていて、`auto-ready`・`auto-in-progress`・`in-progress` のどれかが付いている（判断が出て、再開を待っているか作業中）。
- 次のときは残す。迷ったら残す。
  - `needs-decision` が付いている。
  - 開いていて、ラベルからは判断が出たかわからない（どれも付いていない、など）。
  - Issue が見つからない、照合が1つに決まらない。
- 対象に当たらないタスク（本人が作ったもの、`🤖` で始まっても本人の作業を頼むものなど）には触らない。完了にする以外の操作（書き換え、消す、コメント）はしない。
- 完了にしたタスクと、照合した Issue は、4-7 の開発ログに書く。

### 4-5. 全体を確かめる

1件ずつの確かめとは別に、流れの全体を見る。使うのは、ほかの Issue の一覧（タイトル・開閉・ラベル）、Notion のプロジェクトページ、このプロジェクトの最近の開発ログ、コード。

1. **在庫**: 着手できる Issue（開いていて `auto-ready` が付き、`needs-decision`・`in-progress`・`auto-in-progress` が付いていないもの）が3件以下なら、足りていない。最近の Planner の開発ログを読み、案が出ていない理由を確かめる。
2. **止まっている Issue**: 誰も拾わない Issue がないか。ラベルのない Issue（対話のセッションの作業待ち）、`needs-decision`、`protected`、`in-progress` のまま残っているもの、`auto-blocked` で前提が進む見込みのないもの（前提が上のどれかで止まっている）。そのうち、ほかの Issue や次の段階を止めているものを挙げる。
3. **進み具合**: 設計や計画（どこを見るかはリポジトリの決まりに従う）のどこまで進み、次に進むのを何が止めているか。同じところの手直しが続いて、先に進んでいないことはないか。
4. **手順と記録の古さ**: `.claude/` の手順・README・プロジェクトページが、決まったことやコードと食い違っていないか。`反映待ち` の付いた開発ログが、多くたまっていないか（目安は5件以上）。
5. **線**: Issue が従うべき決まりの「本人に残すもの」に近い作業が、判断のないまま続いていないか（1件ずつでは小さく見えても、合わせると線を越えるもの）。

- 結果は、4-7 の開発ログに「全体の確かめ」の見出しで書く。問題がなければ「問題なし」と1行書く。
- 本人の作業や判断がないと流れが止まる問題（1〜3）を見つけ、同じ内容の開いている Issue がないときは、`needs-decision` の Issue の案を1件だけ書く（`new-NN.md`。止めているもの、頼みたいこと、放っておくとどうなるかを書く）。Todoist の判断待ちの登録先にも、4-3 と同じ形でタスクを1件作る。すでに Issue があるものは、開発ログに書くだけにする。
- 4 と 5 は、開発ログに `反映待ち` を付けて書く。5 で、すでに線を越えているとわかるものは、4-3 の 4 と同じに扱う。
- ここでも、新しい機能や改善の案は出さない。

### 4-6. してはいけないこと

- 4-4 の対象に当たらない Todoist のタスクを完了にすること。Todoist で、タスクの追加（4-3・4-5）と完了（4-4）以外の操作をすること。
- 新しい機能や改善の案を出すこと（Planner の仕事）。ここで書く Issue の案は、マージされた PR の問題を直すものと、4-5 で見つけた、流れを止めている問題を本人に知らせるものだけ。
- Secret・`.env`・認証情報、外部のサイトから取得した HTML・PDF・画像の中身、個人の情報を、結果や記録に書くこと。
- ほかに、リポジトリの決まりの「してはいけないこと」に従う。

### 4-7. 記録する

終わる前に、Notion の開発ログ DB に1行追加する。

- `プロジェクト` のリレーション、`日付`、`種類` = `調査`、`ツール`、`実行` = `自動` を設定する。
- 本文は箇条書きで、見た Issue と PR、止めた・閉じた Issue とその理由、PR から見つけて Issue の案にした問題、問題がなかったもの、完了にした判断待ちのタスク、全体の確かめ（4-5）。
- 同じ種類の問題がくり返し出ているとわかるときは、Planner や Engineer の手順（planner・engineer スキルと、リポジトリの `.claude/planner.md`・`.claude/engineer.md`）の直し方の提案を「プロジェクトページへの反映」の見出しで書き、`反映待ち` を付ける。`.claude/` の変更は、対話のセッションが別の PR にし、本人がマージする。スキルの変更は dotfiles で行う。
- Notion の既存のページは書き換えられない（許されているのはページの追加だけ）。反映は、本人との対話のときに行われる。

## 5. 対話で呼ばれたとき

「この Issue を精査して」「この PR を精査して」などと本人との対話で頼まれたときは、4 の手順で進める。Bot と違うのは次のところだけ。

- 3 の「Bot として動くとき」は当てはまらない。Issue と PR は自分で `gh` で読む（`gh issue view`・`gh pr view`、PR の変更は `gh pr diff` かマージコミットの `git show`）。対話でも、書いた側の考えを引き継がずに読む側として見る。その Issue や PR を書いた会話で頼まれたときは、新しい文脈のサブエージェントに精査させる。
- 結果のファイルは書かない。結果（止める・閉じる Issue とその理由、直す Issue の案、問題がなかったもの）を本人に報告する。
- Issue を止める・閉じる、直す Issue を作る、は本人が了承してから、自分で `gh` で行う。
  - 止める: 理由をコメントし、`auto-ready` を外して `needs-decision` を付ける。閉じる: 理由をコメントし、`gh issue close --reason "not planned"` で閉じる。精査した Issue と PR には `auto-reviewed` を付ける。
  - 直す Issue は、planner スキルの「5. 対話で呼ばれたとき」と同じ書き方で作り、`auto-finding` と `p2` を付ける。
  - コメントと本文に、`🤖 自動開発ワークフロー` で始まる印は書かない。ワークフローが書いたものと見分けがつかなくなるため。
- 判断待ちのタスクの片付け（4-4）と全体の確かめ（4-5）は、頼まれたときだけ行う。Todoist のタスクの完了と追加は、本人が了承してから行う（`~/.claude/CLAUDE.md` の「Todoist」）。
- 記録は `~/.claude/CLAUDE.md` の「作業の記録」に従う。

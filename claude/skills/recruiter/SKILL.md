# Recruiter: 任せる仕組みを設計して作る

本人の仕事に合わせて、Claude に任せる仕組みを設計して作る（採用する）。
採用したあとの見直しは、このスキルでは行わず、Auditor（精査。`auditor` スキル）に任せる。採用した側が見直すと、自分の設計を正しいと思う前提で見てしまうため。
数より質を優先する。新しく作る前に、今ある仕組みを直して済まないかを先に考える。少数の、よく動く仕組みのほうが、寄せ集めより使いやすく、直しやすいため。

## 1. 聞き取る

次をまとめて聞く。AskUserQuestion を使ってよい。会話や Notion ですでにわかっていることは聞かない。

- 何の仕事か。その中で、どの作業に一番時間がかかっているか、毎回うんざりしているか
- いつ動いてほしいか: 頼んだときだけ／決まった時間に／何かが起きたとき（メールが来た、Issue ができた、など）
- 何とやり取りするか: リポジトリ、Notion、Todoist、Gmail、Web、ほかのツール
- 終わったと言える条件と、本人が最後に確かめること（成果物、承認の有無）
- 今、本人が手で運んでいる情報や、コピペしている手順はどこか

## 2. 今あるものを調べる

重ならないよう、作る前に今あるものを見る。

- スキル: `~/.claude/skills/`、そのリポジトリの `.claude/skills/`
- サブエージェント: `~/.claude/agents/`、そのリポジトリの `.claude/agents/`
- 自動開発の手順: そのリポジトリの `.claude/auto-*.md`
- スクリプト: dotfiles の `bin/`、そのリポジトリのスクリプト

近いものがあれば、新しく作るのではなく、それを直す案を先に出す。

## 3. 形を決める

上から順に当てはまるかを見る。上のほうが、毎回同じ結果になり、トークンも少なくて済む。

| 当てはまること | 形 |
|---|---|
| 間違いや漏れを止めたい | Lint・テスト・hook（`settings.json` の hooks） |
| 毎回同じ処理で、判断が要らない | スクリプト |
| 本人が頼んだときに、決まった手順で進めたい | スキル |
| 調べ物やレビューなど、本筋の会話と切り離して任せたい | サブエージェント |
| 決まった時間や、何かが起きたときに動かしたい | 定期実行（クラウドのルーチンは `/schedule`、手元の Mac なら launchd） |

組み合わせてよい。例えば、決まった処理はスクリプトにし、それを呼ぶ手順をスキルにして、定期実行から起動する。
リポジトリの開発作業を自動で進めたいときは、新しい仕組みを作らず、自動開発（`claude-auto-dev`）の Issue にできないかを先に考える。

## 4. 置き場所を決める

- どのリポジトリでも使うもの: dotfiles（`claude/skills/`、`bin/` など）。dotfiles は公開なので、個人の情報・案件の名前・URL を含むものは入れない
- リポジトリに固有のもの: そのリポジトリの `.claude/` など
- 個人の情報を含み、どのリポジトリでも使うもの: 置き場所を本人と決める

## 5. 言い直して確かめる

作る前に、次を自分の言葉で短く言い直し、本人に確かめる。ずれていたらここで直す。

- 何を任せるか、いつ動くか、何とやり取りするか
- 選んだ形と、その理由
- 置き場所と、終わったと言える条件

## 6. 作る

- スキル: frontmatter の `description` に、何をするかと、どんな頼まれ方で使うかを書く。本文は手順だけを短く書く。判断の要らない処理はスクリプトに出す
- サブエージェント: 役割・使ってよいツール・返す内容を絞る
- スクリプトとテスト: CLAUDE.md の TDD の決まりどおり、テストを先に書く
- ファイルの変更は、CLAUDE.md の決まりどおり、ブランチを切って PR にする。`claude/` や `.claude/` の変更は自動ではマージされないので、ほかの変更と PR を分ける

## 7. 試す

実際の作業を1件、作ったもので動かし、結果を本人と一緒に見る。直すところがあれば、文章の手順を足す前に、スクリプトや Lint などの仕組みで直せないかを考える。

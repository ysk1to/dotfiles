# Evaluator: 仕組みの働きぶりを評価する

Bot とスキルの全部を、記録をもとに評価する。Recruiter（`recruiter` スキル）が採用したものに限らない。
評価して案を出すところまでを受け持つ。直すか、消すかは本人が決める。直すときは、本人が了承してから対話で行う。
対話でも、自動開発の Bot としても、同じ手順（0〜4）で進める。Bot として動くときの取り決めと、手順のうち Bot で違うところは 5 に書く。

## 0. 文脈を分ける

この会話で、評価する仕組みを作ったり直したりしていたら、Agent ツールで新しい文脈のサブエージェントに 1〜3 を任せる。渡すのは、このスキルのパスと評価の期間だけにし、作ったときの理由や経緯は渡さない。作った側の見方が入ると、自分の設計を正しいと思う前提で見てしまうため。
`claude -p` などの自動実行で呼ばれたときは、もともと新しい文脈なので、そのまま進める。

## 1. 材料を集める

- 集計: `~/bin/claude-bot-stats --days <日数>`（既定は7日）。役割ごとの回数・PR・Issue・判断待ち・失敗、PR の自動マージ・要確認・レビュー前の数、スキルが呼ばれた回数が出る。数は自分で数え直さず、この出力を使う
- 仕組みの中身: スキルの `SKILL.md`（`~/.claude/skills/`、各リポジトリの `.claude/skills/`）、自動開発の手順（各リポジトリの `.claude/auto-*.md`）、PR の自動レビュー（各リポジトリの `.github/workflows/pr-review.yml`）
- 要確認になった PR の自動レビューのコメント、判断待ちの Issue のコメント（どの指摘・判断が多いか）
- Notion の開発ログ（その期間のもの）。本人に直された・同じ指摘が続いた、という記録を探す

## 2. 評価する

仕組みごとに、次を短くまとめる。数字は 1 の集計から引き、推測で書かない。

- うまく動いているか: 回数・成功・失敗・判断待ち・要確認の割合から見る
- ずれている所: 同じ失敗・同じ指摘・同じ判断待ちが繰り返されていないか。ずれの原因は、聞き取りの不足、手順のあいまいさ、道具の不足のどれか
- 直す案: 同じずれが2回以上あるなら、手順の文章を足すのではなく、スクリプト・Lint・テスト・hook で止める案を出す
- 消す・まとめる案: 期間内に使われていない、ほかと役目が重なっているもの

うまく動いていて直す所がない仕組みは、一覧に1行で書くだけにする。

## 3. 記録する

- 評価を、Notion の開発ログ（ハブの開発ログ DB、プロジェクトは dotfiles、種類は「調査」）に1件書く。タイトルは「仕組みの評価（期間）」にする
- dotfiles は公開リポジトリなので、評価を dotfiles の Issue や PR には書かない。リポジトリ名・Issue の中身・会話の中身を含むため
- 本人の判断が要る案（直すか、消すか）は、まとめて本人に提案する。対話では Todoist への登録を提案し、了承を得てから登録する。自動実行では、CLAUDE.md の「自動実行中の判断待ち」の決まりどおり、了承なしで登録してよい

## 4. 伝える

本人には、評価の要点だけを短く伝える。直す案が多いときは、効き目の大きい順に3つまでにし、残りは Notion にあると添える。

## 5. Bot として動くとき

起動時のプロンプトに「自動開発ワークフロー」とあるときは、手元の Mac の launchd から週に1回起動される Bot（dotfiles の `claude-auto-dev` の Evaluator の回）として動いている。
起動したときに人はいないので、確認を待たずに手順どおり進める。手順は 0〜4 と同じで、違うのは次のところだけ。

起動時のプロンプトには、このスキルの本文と、リポジトリの決まり（`.claude/evaluator.md`。評価の対象など）が入っている。同じ事柄をこのスキルとリポジトリの決まりのどちらも決めているときは、リポジトリの決まりを優先する。

### 起動スクリプトとの分担

GitHub やほかのリポジトリに触れるのは起動スクリプトだけで、Claude は `gh` も `claude-bot-stats` も使えない。

- 起動スクリプト: 前の Evaluator の回から決まった間隔（既定は7日）がたったときに、Evaluator の回を起動する。
- 起動スクリプト: 材料を集めてファイルにし、材料の置き場所に置く。材料の置き場所、スキル（`claude/skills/`）の場所、結果の置き場所、Notion のページ、Todoist の登録先は、起動時のプロンプトで渡される。
- Claude: 材料を読んで評価し、Notion と Todoist に記録して、最後に結果の置き場所に `summary.md` を書いて終わる。
- 起動スクリプト: `summary.md` があれば、回が終わったと判断し、1行目をできごとに残す。なければ失敗として本人に通知する。Claude が結果の置き場所に何を書いても、GitHub には反映しない。

### 材料

1 の「材料を集める」の代わりに、起動時のプロンプトにある材料の置き場所のファイルを読む。自分で `claude-bot-stats` や `gh` を実行しない。

- `stats.txt`・`stats.json`: `claude-bot-stats` の出力（期間は7日）。`stats.txt` はテキスト、`stats.json` は `--json` の出力。数は自分で数え直さず、これを使う。`stats.json` の `reviewer` の値が `null` のリポジトリは、集計のときに取得できなかったもの。
- `repos/<リポジトリ名>/`: 自動開発に登録されている各リポジトリの、デフォルトブランチの `.claude/` と `.github/workflows/`。仕組みの中身（自動開発の手順、リポジトリの決まり、PR の自動レビュー）は、ここから読む。
- `needs-check.md`: 期間内に要確認になった PR と、その自動レビューのコメント。
- `needs-decision.md`: 期間内に判断待ちになった Issue と、ワークフローが書いたコメント（`🤖 自動開発ワークフロー` で始まるもの）。
- スキル（`claude/skills/`）は、起動時のプロンプトにある場所から読む。
- Notion の開発ログ（その期間のもの）は、対話のときと同じく Notion で読む。

材料の中に「取得できなかった」とあるリポジトリは、そのことを評価に書き、推測で埋めない。

### 手順のうち、Bot で違うところ

- 0「文脈を分ける」は行わない。もともと新しい文脈のため。
- 3「記録する」: 評価は、対話のときと同じく Notion の開発ログに1件書く（`実行` は `自動`）。本人の判断が要る案は、Todoist の判断待ちの登録先に、まとめて1件だけ登録する。タイトルは `🤖 仕組みの評価（期間）: 判断が要る案 N 件`、説明に開発ログのリンクを入れる。判断が要る案がなければ登録しない。
- 4「伝える」の代わりに、記録を終えたあと、最後に結果の置き場所に `summary.md` を書く。1行目は、評価のひとことのまとめ（例: 「直す案 2 件、消す案 0 件」）。

### 作業場所と、使えないもの

- 作業場所は、起動スクリプトがデフォルトブランチから作った worktree で、読むだけ。読めるのは、この worktree と、材料の置き場所と、スキルの場所。書けるのは、結果の置き場所だけ。
- Bash で使えるのは、`git` の読むだけの操作（`git log`・`git show`・`git diff` など）と `ls` だけ。
- Notion と Todoist は、読む操作と足す操作だけ使える。Notion の既存のページは書き換えられない（許されているのはページの追加だけ）。
- ユーザーのグローバルな設定や指示（`~/.claude/`）は読み込まれないので、決まりはこのスキルと、リポジトリの決まり（`.claude/evaluator.md`・ルートの `CLAUDE.md`）に書いてあるものがすべて。
- Web の取得もできない。
- 文章は日本語で書く。
- ワークフローは本人の GitHub アカウントで動く。起動スクリプトが書くコメントは、`🤖 自動開発ワークフロー` で始まる（`🤖 自動開発ワークフロー: …`、`🤖 自動開発ワークフロー（…）: …`）。

### してはいけないこと

- `gh` や `claude-bot-stats` を使うこと。材料は起動スクリプトが渡す。
- GitHub に何かを書くこと（Issue・PR・コメントを作ること）。評価には、ほかのリポジトリの名前や中身が入るため。
- 仕組み（スキル・リポジトリの決まり・ワークフロー）を直すこと。直すかは本人が決め、直すときは対話で行う。

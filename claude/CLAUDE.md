# 全般
- 応答は常に日本語で行う。
- `rm -rf /` など、システム全体を破壊しうるコマンドは絶対に実行しない。
- 記事、ドキュメント、PR の説明文、コミットメッセージなどの日本語の文章を書いたり直したりするときは、常に yomiyasu スキルで推敲する。コードを直したあとの作業の報告には使わなくてよい。

# Git コミットメッセージ
作業内容を表す接頭辞を付け、その後に日本語で1行にまとめる。例: `[fix] ログイン時のセッション切れを修正`
- Claude Code がコミットするときは、先頭に `🤖` と半角スペースを付ける。例: `🤖 [fix] ログイン時のセッション切れを修正`
- `Co-Authored-By` などの署名行は付けない。

| 接頭辞 | 用途 |
|---|---|
| `[add]` | 新機能や新ファイルを追加 |
| `[update]` | 既存機能の改善や更新 |
| `[fix]` | バグ修正 |
| `[refactor]` | リファクタリング |
| `[remove]` | ファイルや機能の削除 |
| `[style]` | コードスタイルの修正 |
| `[docs]` | ドキュメントの更新 |
| `[test]` | テスト関連の変更 |

# ブランチとプルリクエスト
`main` には直接コミットもマージもしない。変更は必ずプルリクエストを通して取り込む。
- 作業を始めるときは `main` から作業ブランチを切る。ブランチ名は英小文字とハイフンで内容を表す。例: `add-chart`、`fix-session-timeout`
- 手元で `main` にマージしない。作業ブランチを push し、`gh pr create` でプルリクエストを作る。
- プルリクエストのタイトルはコミットメッセージと同じ形式にする。Claude Code が作るときは先頭に `🤖` を付ける。例: `🤖 [add] 候補のチャートを HTML に書き出す chart コマンドを追加`
- 本文は日本語で、次の見出しで書く。
  - `## 概要`: 何のための変更か
  - `## 変更点`: 主な変更の箇条書き
  - `## 確認したこと`: テストや動作確認の結果。確認していないことも書く
- 本文に `Generated with Claude Code` などの署名行は付けない。
- Claude Code は自分でプルリクエストをマージしない。`main` への push も、ユーザーの指示があったときだけ行う。
- ブランチの削除: プルリクエストがマージ済みだと `gh pr list --head <ブランチ> --state merged` で確かめたブランチは、指示がなくても手元から消してよい（`main` に切り替えて最新にしてから `git branch -D`、`git fetch --prune`）。リモートのブランチは、GitHub の「Automatically delete head branches」が有効ならマージ時に消える。それ以外のブランチの削除は、ユーザーの指示があったときだけ行う。

## 自動レビュー
- 新しいリポジトリを作ったとき、またはワークフローがないリポジトリで開発を始めるときは、`.github/workflows/pr-review.yml` を導入する。雛形は dotfiles（`ysk1to/dotfiles`）のものを使い、リポジトリに合わせて次を変える。
  - Lint とテストのステップ: そのリポジトリの標準コマンドにする（言語ごとの標準コマンドを参照）。OS 依存のコマンドがあればランナーを合わせる。
  - レビューのプロンプト: 冒頭のリポジトリの説明を書き換え、見ることに、リポジトリに載せてはいけないもの（データ、個人情報など）や独自の決まりを書く。
  - 自動でマージしない対象: `.github/` と、Claude への指示（`CLAUDE.md`・`.claude/` など）がある場所。「この PR で古くなる記述（followups）」の説明と、受け付けるファイルの判定も同じ対象にする。自動開発のあるリポジトリでは、作る Issue に `protected` を付ける。
- 導入の PR を作ったら、Secret の `CLAUDE_CODE_OAUTH_TOKEN` の登録を本人に頼む（`claude setup-token` で作り、`gh secret set CLAUDE_CODE_OAUTH_TOKEN -R <リポジトリ>` で登録）。導入の PR は `.github/` の変更なので、本人がマージする。
- 試作や使い捨てのリポジトリでは導入しない。

リポジトリに `.github/workflows/pr-review.yml` がある場合、プルリクエストを作ると GitHub Actions で Claude がレビューする。問題がなければそのままマージされ、判断が必要なときは PR にコメントしてユーザーをメンションする。
- プルリクエストを作ったら、レビューの実行が終わるまでバックグラウンドで待つ（例: `gh pr checks <PR番号> --watch`）。
- 終わったら、`gh pr view --json state,comments` で結果を確かめる。
  - マージされたとき: 手元の作業ブランチを消して `main` を最新にし、一言で報告する。通知はしない。
  - マージされなかったとき: PushNotification でユーザーに通知し（例: `PR #3 要確認: テスト不足の指摘`）、コメントの指摘の要点を伝える。指摘への対応は、ユーザーの判断を聞いてから行う。
- 指摘に対応して push すると、もう一度レビューが走る。そのときも同じように待って結果を伝える。
  - 再レビューも PR 全体を見直すが、前回のレビューのコメントを受け取り、前回の指摘が直ったかを、コメントの「前回の指摘」の節に書く。結果を伝えるときは、残っている指摘と新しい指摘を中心にする。
- 自動でマージさせたくないプルリクエストには、`no-auto-merge` ラベルを付ける。`.github/`・`CLAUDE.md`・`.claude/` を変える PR は、ワークフローが自動ではマージしない。
- ワークフローが自動でマージしないファイル（`.github/`・`CLAUDE.md`・`.claude/` など。対象は、各リポジトリの `.github/workflows/pr-review.yml` にある判定で決まる）を変えるときは、ほかの変更と同じ PR に入れず、別の PR に分ける。1つでも入っていると、PR 全体が自動でマージされないため。
  - 分けた PR を先に出し、ユーザーにマージしてもらう。CI や手順の変更を先に入れておくと、本体の PR はそれを使ってレビューされる。
  - 本体の PR は、分けた PR がマージされてから、最新の `main` の上で作る。
  - 本体の変更で、これらのファイルの記述（`CLAUDE.md` の説明など）が古くなるだけのときは、本体の PR を先に出してよい。自動レビューは止めずにマージし、古くなった記述を直す Issue を作る。その Issue を、別の PR で直す。
- ワークフローがないリポジトリでは、マージはユーザーの指示があったときだけ行う。

## 並行作業と Issue
リポジトリに `auto-ready` ラベルがある場合は、自動開発ワークフロー（`claude-auto-dev`）やほかの対話のセッションと並行して作業が進む。ぶつからないよう、対話のセッションでも次のようにする。
- ファイルを変える作業は、Issue を作ってから始める。依頼された作業に合う Issue がなければ作る（タイトルの先頭に `🤖`、本文に何をするか・範囲・完了の条件）。調べ物だけ、質問への回答だけ、のような変更のない作業では作らない。
- 着手する前に、Issue のラベルを見る。`auto-in-progress`（自動開発が作業中）か `in-progress`（ほかの対話のセッションが作業中）が付いていたら着手せず、ユーザーに伝える。
- 同じディレクトリを触る作業中の Issue（`in-progress`・`auto-in-progress`）や、開いている PR があれば、着手する前にユーザーに伝える。マージのときにぶつかるため。
- 着手するときは `in-progress` を付け、`auto-ready` が付いていれば外して、`🤖 対話のセッションで着手` とコメントする。
- 作業は `main` から作った worktree で行う。本人の作業ツリーや、ほかのセッションの worktree は使わない。ブランチ名は `auto-` で始めない（自動開発のブランチと区別するため）。
- PR の本文の末尾に `Closes #<番号>` を入れる。
- 途中でやめるときは `in-progress` を外し、どこまで進んだかを Issue にコメントする。`auto-ready` に戻すかは、ユーザーが決める。

# Notion
Notion MCP は本人のアカウントで接続しているため、作成者や編集履歴では Claude が書いたかどうかを判別できない。Claude Code が書いたものは、次のように見分けられるようにする。
- ページを作るときは、タイトルの先頭に `🤖` と半角スペースを付ける。例: `🤖 2. 全体設計`
- データベースにページを作るときは、`作成者` プロパティを `Claude` にする。プロパティがないデータベースでは、追加してよいかをユーザーに聞いてから追加する。
- 人が書いたページを一部だけ直したときは、追記した部分の近くに `🤖 Claude が追記（YYYY-MM-DD）` と小さく書き添える。
- 既存のページを書き換えたり消したりする前に、ユーザーに確認する。ただし、下の「作業の記録」でハブに Claude が作ったページは確認せずに更新してよい。

## 作業の記録（指示がなくても行う）
Claude と Claude Code の作業は、Notion のハブ「🤖 Claude ワークスペース」に記録する。ハブと DB の URL は次のファイルにある（Git 管理外）。
@~/.claude/notion-hub.local.md

- **プロジェクト**: 作業を始めるとき、リポジトリの `CLAUDE.local.md` に、ハブのプロジェクトページの URL が書いてあるかを見る。
  - なければ、プロジェクト DB を検索する。それでもなければ、1行作る（`作成者` = `Claude`）。作ったら `CLAUDE.local.md` に URL を書く（`.gitignore` に入っているかも確かめる）。
  - 調べ物だけ、質問への回答だけ、のような小さな作業ではプロジェクトを作らない。
- **現状と決定事項**: プロジェクトページの本文。設計・方針・未決事項を、常に最新の状態に**上書き**する。決まったことは理由も一緒に書く。
  - 自動実行（`claude-auto-dev`）は既存のページを書き換えられないので、プロジェクトページに反映すべきことがある開発ログに `反映待ち` のチェックを付ける。作業を始めるとき、そのプロジェクトの `反映待ち` が付いた開発ログを検索し、内容をプロジェクトページに反映してからチェックを外す。Issue にするかなど本人の判断が要るものは、反映したうえで本人に伝える。
- **開発ログ**: 開発ログ DB に**追記**する。`プロジェクト` のリレーション、`日付`、`種類`（決定・実装・調査・設定・その他）、`ツール`、`作成者` = `Claude` を設定し、PR などがあれば `リンク` に入れる。本文は箇条書きで、何をしたか・なぜか・次にやることを書く。
- **記録するタイミング**: 区切りだけ。方針が決まったとき、PR を作ったとき、作業が一区切りしたとき、セッションを終えそうなとき。毎ターンは書かない。記録したら、応答の最後に一言だけ添える（例: 「Notion に記録しました」）。
- **本人の情報**: 本人の役割・好み・共通の方針・環境など、長く役立つ情報が会話に出てきたら、Notion Memory（`parent: "memory"`）に保存するかを一言提案する。保存は本人が了承してから行う。一時的な進捗や、リポジトリを見ればわかることは提案しない。Memory は Notion の `Created by` で Claude と表示されるので、`🤖` や `作成者` は付けない。
- 本人が書くノート（例: 本人の調べ物のページ）は記録先にしない。そこへ書き戻すときは、上のルールどおり了承を得る。

# Todoist
会話の中で、本人の判断や本人にしかできない行動が会話の外に残るとき（決めきれなかったこと、本人がやる作業・手続き・連絡、期限のあるもの）は、区切りのタイミングで Todoist に登録するかをまとめて提案する。
- 開発に限らず、どの話題でも対象にする。
- 登録は本人が了承してから行う。登録先は既存のプロジェクトから内容に合うものを選び、合うものがなければインボックスにする（提案のときに登録先も示す）。
- 関連する Notion ページや PR などのリンクがあれば添える。
- Claude が次に続ければよい作業は登録せず、Notion の開発ログなどに書く。

## 自動実行中の判断待ち（了承なしで登録してよい例外）
ルーチンや `claude -p` などの自動実行中に本人の判断が必要になったときは、了承を待たずに Todoist に登録してよい。登録してよいのは判断待ちだけで、それ以外のタスクは作らない。
- 登録先: 次のファイル（Git 管理外）に書いたプロジェクトの、開発案件と同じ名前のセクション（例: `my-app`）。セクションがなければ、リポジトリ名で作る。
@~/.claude/todoist.local.md
- タイトルの先頭に `🤖` と半角スペースを付け、自動実行中に登録したとわかるようにする。案件名はセクションでわかるので、タイトルには入れない。例: `🤖 #12 キャッシュの保持期間を決める`
- 説明に、判断の材料がある Issue や PR のリンクを入れる。議論は Issue や PR のコメントで行い、Todoist には書かない。
- 判断が出て作業を再開したら、自分で作ったそのタスクを完了にする。本人が作ったタスクは変更も完了もしない。

# テスト駆動開発（TDD）
コードの変更は、必ずテストを先に書いてから実装する。
1. **Red**: 期待する振る舞いを表すテストを1つ書き、実行して失敗することを確かめる。失敗の理由が想定どおり（未実装や期待値の違い）であることも見る。コンパイルエラーのままにしない。
2. **Green**: そのテストが通る最小限の実装をする。テストを実行して、通ることと既存のテストが壊れていないことを確かめる。
3. **Refactor**: テストが通る状態を保ったまま整理する。整理のたびにテストを実行する。
- 1サイクルは小さく保ち、振る舞いを1つずつ足していく。
- バグ修正は、まずそのバグを再現する失敗テストを書いてから直す。
- テストを通すために、テストの期待値を実装に合わせて書き換えない。仕様が変わった場合は、そのことをユーザーに伝えてから直す。
- テストと実装は同じコミットに入れる。プルリクエストの「確認したこと」には、追加したテストを書く。
- テストを先に書けない変更（ドキュメントだけの変更、捨てる前提の試作、画面の見た目の調整など）は、その理由をユーザーに伝えてから進める。試作のコードはそのままリポジトリに入れず、テストから書き直す。

# 言語ごとの標準コマンド（プロジェクト側に指定がなければこれを使う）
- Go: フォーマット `gofmt -w .` / Lint `golangci-lint run` / テスト `go test ./...`
- PHP: フォーマット `composer run phpcbf` / Lint `composer run phpcs` / テスト `composer test`

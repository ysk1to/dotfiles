# 全般
- 応答は常に日本語で行う。
- `rm -rf /` など、システム全体を破壊しうるコマンドは絶対に実行しない。

# Git コミットメッセージ
作業内容を表す接頭辞を付け、その後に日本語で1行にまとめる。例: `[fix] ログイン時のセッション切れを修正`
- Claude Code がコミットするときは、先頭に `🤖` と半角スペースを付ける。例: `🤖 [fix] ログイン時のセッション切れを修正`
- `Co-Authored-By` などの署名行は付けない。

| 接頭辞 | 用途 |
|---|---|
| `[add]` | 新機能や新ファイルを追加 |
| `[update]` | 既存機能の改善や更新 |
| `[fix]` | バグ修正 |
| `[refactor]` | リファクタリング |
| `[remove]` | ファイルや機能の削除 |
| `[style]` | コードスタイルの修正 |
| `[docs]` | ドキュメントの更新 |
| `[test]` | テスト関連の変更 |

# ブランチとプルリクエスト
`main` には直接コミットもマージもしない。変更は必ずプルリクエストを通して取り込む。
- 作業を始めるときは `main` から作業ブランチを切る。ブランチ名は英小文字とハイフンで内容を表す。例: `add-chart`、`fix-session-timeout`
- 手元で `main` にマージしない。作業ブランチを push し、`gh pr create` でプルリクエストを作る。
- プルリクエストのタイトルはコミットメッセージと同じ形式にする。Claude Code が作るときは先頭に `🤖` を付ける。例: `🤖 [add] 候補のチャートを HTML に書き出す chart コマンドを追加`
- 本文は日本語で、次の見出しで書く。
  - `## 概要`: 何のための変更か
  - `## 変更点`: 主な変更の箇条書き
  - `## 確認したこと`: テストや動作確認の結果。確認していないことも書く
- 本文に `Generated with Claude Code` などの署名行は付けない。
- Claude Code は自分でプルリクエストをマージしない。`main` への push も、ユーザーの指示があったときだけ行う。
- ブランチの削除: プルリクエストがマージ済みだと `gh pr list --head <ブランチ> --state merged` で確かめたブランチは、指示がなくても手元から消してよい（`main` に切り替えて最新にしてから `git branch -D`、`git fetch --prune`）。リモートのブランチは、GitHub の「Automatically delete head branches」が有効ならマージ時に消える。それ以外のブランチの削除は、ユーザーの指示があったときだけ行う。

## 自動レビュー
リポジトリに `.github/workflows/pr-review.yml` がある場合、プルリクエストを作ると GitHub Actions で Claude がレビューする。問題がなければそのままマージされ、判断が必要なときは PR にコメントしてユーザーをメンションする。
- プルリクエストを作ったら、レビューの実行が終わるまでバックグラウンドで待つ（例: `gh pr checks <PR番号> --watch`）。
- 終わったら、`gh pr view --json state,comments` で結果を確かめる。
  - マージされたとき: 手元の作業ブランチを消して `main` を最新にし、一言で報告する。通知はしない。
  - マージされなかったとき: PushNotification でユーザーに通知し（例: `PR #3 要確認: テスト不足の指摘`）、コメントの指摘の要点を伝える。指摘への対応は、ユーザーの判断を聞いてから行う。
- 指摘に対応して push すると、もう一度レビューが走る。そのときも同じように待って結果を伝える。
- 自動でマージさせたくないプルリクエストには、`no-auto-merge` ラベルを付ける。`.github/`・`CLAUDE.md`・`.claude/` を変える PR は、ワークフローが自動ではマージしない。
- ワークフローがないリポジトリでは、マージはユーザーの指示があったときだけ行う。

# Notion
Notion MCP は本人のアカウントで接続しているため、作成者や編集履歴では Claude が書いたかどうかを判別できない。Claude Code が書いたものは、次のように見分けられるようにする。
- ページを作るときは、タイトルの先頭に `🤖` と半角スペースを付ける。例: `🤖 2. 全体設計`
- データベースにページを作るときは、`作成者` プロパティを `Claude` にする。プロパティがないデータベースでは、追加してよいかをユーザーに聞いてから追加する。
- 人が書いたページを一部だけ直したときは、追記した部分の近くに `🤖 Claude が追記（YYYY-MM-DD）` と小さく書き添える。
- 既存のページを書き換えたり消したりする前に、ユーザーに確認する。

# テスト駆動開発（TDD）
コードの変更は、必ずテストを先に書いてから実装する。
1. **Red**: 期待する振る舞いを表すテストを1つ書き、実行して失敗することを確かめる。失敗の理由が想定どおり（未実装や期待値の違い）であることも見る。コンパイルエラーのままにしない。
2. **Green**: そのテストが通る最小限の実装をする。テストを実行して、通ることと既存のテストが壊れていないことを確かめる。
3. **Refactor**: テストが通る状態を保ったまま整理する。整理のたびにテストを実行する。
- 1サイクルは小さく保ち、振る舞いを1つずつ足していく。
- バグ修正は、まずそのバグを再現する失敗テストを書いてから直す。
- テストを通すために、テストの期待値を実装に合わせて書き換えない。仕様が変わった場合は、そのことをユーザーに伝えてから直す。
- テストと実装は同じコミットに入れる。プルリクエストの「確認したこと」には、追加したテストを書く。
- テストを先に書けない変更（ドキュメントだけの変更、捨てる前提の試作、画面の見た目の調整など）は、その理由をユーザーに伝えてから進める。試作のコードはそのままリポジトリに入れず、テストから書き直す。
